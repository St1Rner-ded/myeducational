## 1. L0-T2 — принято

```cpp
if (n<2) return false;
if (n%2==0) { if (n==2) return true; else return false; }
for (long long d=3; d<=n/d; d+=2) if (n%d==0) return false;
return true;
```

Все 24 теста, включая `121`, `10201`, `3215031751` и `999985999949`. И главное —
ты взял **`d <= n / d`**, то есть безопасную форму условия, а не `d * d <= n`.
Это ровно та мина, которая на `INT_MAX` даёт UB, 15 секунд работы и неверный ответ.

Что поджать по стилю:

```cpp
if (n < 2) return false;
if (n % 2 == 0) return n == 2;      // вместо вложенного if/else — выражение и есть ответ
for (long long d = 3; d <= n / d; d += 2)
    if (n % d == 0) return false;
return true;
```

`if (n % 2 == 0) return n == 2;` — одна строка вместо четырёх, и читается как мысль:
«если чётное — простое только когда это двойка». Приём «возвращай результат сравнения,
а не ветку if» пригодится постоянно.

Плюс пробелы: `n<2` → `n < 2`, `d=3` → `d = 3`. Это не придирки — `clang-format`
настроится один раз и сделает сам.

## 2. M2-T1 — принято

```cpp
while (n) { if (n & 1u) ++c; n >>= 1; }
```

Ровно то, что советовал: счётчик убран, второе условие остановки исчезло, ошибка
«не дошёл до старшего бита» стала невозможной конструктивно.

Мелочь: `while (n != 0)` читается лучше, чем `while (n)` — для `unsigned` они
эквивалентны, но явное сравнение с нулём понятнее при чтении чужого кода.

### Дополнение к твоему ответу на вопрос 4

Ты ответил верно: для `n = 1` — одна итерация у обеих версий, для `0xFFFFFFFF` — 32 у обеих.
Но разница между v1 и v2 видна на **разреженных** числах:

| вход | v1 (сдвиги) | v2 (`n & (n-1)`) |
|---|---|---|
| `1` | 1 | 1 |
| `0xFFFFFFFF` | 32 | 32 |
| **`0x80000000`** | **32** | **1** |
| `0x80000001` | 32 | 2 |

v2 делает ровно столько итераций, сколько единиц, — поэтому в реальных библиотеках
используют его (или аппаратную инструкцию `POPCNT`, если она есть).

## 3. Разбор твоих ответов в `notes/M2.md`

### Вопрос 1 · `n & (n-1)` — ✅ хорошо

Разбор на `0b1100` верный, продолжение до `0b1000 & 0b0111 = 0` — тоже.

Отдельно отмечу: ты **зачеркнул своё рассуждение про порядок `++c` и сам себя поправил** —
«проверка условия несовпадения с нулём в любом случае происходит до движений битов».
Вот это и есть настоящая учёба. Оставить зачёркнутую ошибку полезнее, чем стереть:
через месяц ты увидишь, как именно думал неправильно.

Добавлю общую формулировку, которой у тебя не хватило:

> При вычитании 1 младший **единичный** бит становится нулём, а все нули **ниже него** —
> единицами. Биты выше не меняются. Поэтому `n & (n-1)` обнуляет ровно младшую единицу.

И про твою ремарку «выходит `0b11011`, но пятый бит отбрасываем» — ты применил
**арифметику по модулю 2ⁿ**, даже не назвав её. Это ровно §4.1 справочника:
для беззнаковых типов переполнение определено как отбрасывание старшего разряда.
Ты это уже понимаешь интуитивно, осталось закрепить термином.

### Вопрос 2 · `unsigned` против `int` — ❌ ошибка, важная

Ты написал, что для знакового `−8 = 0b11000` сдвиг вправо даст `0b01100 = 12`.

**Наоборот.** Для знаковых типов `>>` — **арифметический** сдвиг: освободившийся старший
разряд заполняется **знаковым битом**, а не нулём.

```
 5-битное знаковое:  -8 = 0b11000
 0b11000 >> 1  =  0b11100  =  -4      ← арифметический (знаковый) сдвиг
                                          заполнили старший разряд единицей
 0b11000 >> 1  =  0b01100  =  +12     ← так было бы для UNSIGNED
                                          (логический сдвиг, заполнение нулями)
```

То есть `12` ты получил бы как раз для **беззнакового** числа `0b11000 = 24`.
Ты переставил местами поведение знакового и беззнакового сдвига.

Точные факты, которые стоит запомнить:

| Тип | `>>` называется | Чем заполняется | Определён стандартом |
|---|---|---|---|
| `unsigned` | логический | нулями | ✅ всегда |
| `signed`, `x ≥ 0` | — | нулями | ✅ |
| `signed`, `x < 0` | **арифметический** | **знаковым битом** | ⚙️ до C++20 implementation-defined, с C++20 — стандартом (все реальные компиляторы делали так всегда) |

Практический вывод: **причина брать `unsigned` не в том, что знаковый сдвиг «сломается»**,
а в том, что для `unsigned` поведение гарантировано стандартом и одинаково везде,
а для `signed` отрицательных значений ты зависишь от реализации. Плюс для `unsigned`
`n >> 1` всегда точно равно `n / 2`.

### Вопрос 3 · `n >> 1` против `n / 2` — вот ответ, которого у тебя не было

Ты написал, что «объяснение как будто дал в предыдущем вопросе». Нет — это отдельный
вопрос, и он интересный:

| выражение | результат | правило |
|---|---|---|
| `-7 / 2` | **−3** | деление округляется **к нулю** |
| `-7 >> 1` | **−4** | арифметический сдвиг округляет **вниз**, к −∞ |

Проверено на gcc: именно −3 и −4. Для положительных чисел они совпадают, для
отрицательных расходятся на единицу.

Это не академический вопрос: если ты считаешь индекс или координату и где-то может появиться
отрицательное значение, `>> 1` и `/ 2` дадут разные ответы, и получится off-by-one.

### Вопрос 4 · итерации — ✅ верно

См. дополнение про разреженные числа выше.

## 4. Презентация `tipy_peremennyh_c_cpp.pptx`

Материал качественный: структура логичная, примеры компилируемые, `volatile uint32_t *port
= (uint32_t *)0x40021000` на слайде 10 — отличный embedded-пример, ровно твоя тема.
Но есть что поправить.

### Фактические ошибки

**1. Слайд 6: «Строки: в C — массив `char*` с terminator-байтом `'\0'`»**

Неверно. Строка в C — массив **`char`**, а не `char*`:

```c
char s[] = "hi";   // массив из 3 байт: 'h','i','\0'   → sizeof s == 3
char *p  = "hi";   // указатель на литерал              → sizeof p == 8
```

Это ровно тот вопрос A7 из диагностики, который ты не знал. Ошибка в конспекте опасна
тем, что ты её заучишь.

**2. Слайд 11: «Почти любой код на C корректен и в C++»**

Вводит в заблуждение: **C++ не является надмножеством C**. Проверенные контрпримеры:

| Код | C | C++ |
|---|---|---|
| `sizeof('A')` | **4** (тип `int`) | **1** (тип `char`) |
| `int *p = malloc(4);` | ✅ компилируется | ❌ нужен `static_cast<int*>` |
| `char *s = "hello";` | ✅ (плохая практика) | ❌ нужен `const char*` |
| `f()` в объявлении | функция с любым числом аргументов | функция без аргументов |

Правильная формулировка: «большинство C-кода компилируется как C++, но есть известные
расхождения». В справочнике это §8.

### Неточности

**3. Слайд 3: `char` … «−128 … 127».** Знаковость `char` implementation-defined:
на x86 знаковый, на ARM часто беззнаковый. На слайде 6 ты об этом пишешь, на слайде 3 —
нет. Несогласованность между слайдами хуже, чем отсутствие оговорки в одном месте.

**4. Слайд 4: `int32_t x = -2147483648;`.** Скомпилируется, но литерал парсится как
«минус, применённый к `2147483648`», а это число **не влезает в `int`**. Безопасная
запись — `INT32_MIN`. Мелочь, которая однажды выстрелит на другой платформе.

**5. Слайд 10 про `volatile`.** Стоит добавить важное: `volatile` **не даёт атомарности**
и **не упорядочивает** обращения относительно других потоков или прерываний. Он защищает
только от оптимизатора. Для embedded это частая ловушка: `volatile` в обработчике
прерывания сам по себе не спасает от гонки.

### Чего не хватает (и это ровно твои дыры)

- Переполнение знакового типа = **UB**, беззнакового = **wraparound**. На слайдах этого нет
  вообще, а у тебя был неверный ответ на A9 и правильный на A8 — тема не закреплена.
- Тип `size_t`: на слайде 4 используется `%zu`, но что это за тип — не сказано. А это
  причина твоего A11 (`v.size() - 1` = 18 квадриллионов).
- Спецификаторы `printf` (`%zu`, `%lld`, `%x`) — в справочнике §2.1.

### Вывод по презентации

Учить по ней можно, но с поправками выше. Главный урок другой: **сгенерированный
ИИ учебный материал надо проверять**. Две фактические ошибки на 12 слайдов — это
хороший результат для ИИ, но если их заучить, они обойдутся дороже, чем отсутствие
презентации. Сверяй со справочником §1 и §8 — там те же темы, но числа получены
запуском компилятора.

## 5. Arduino-проект `scratch/trsomething/ARDUINO/main.cpp`

Проект хороший: 4-разрядная динамическая индикация, гашение незначащих разрядов,
корректный порядок обновления (сначала погасить все разряды → выставить сегменты →
включить нужный → задержка). Кадр из 4 разрядов по 5 мс = 20 мс = 50 Гц — мерцания
не будет, частота выбрана правильно.

**И главное: ты там уже делаешь модуль 2**, просто не называешь это так:

| В твоём коде | Что это в терминах модуля 2 |
|---|---|
| `digs[10] = {0b11111100, ...}` | таблица **битовых масок** сегментов |
| `bitRead(digs[curDigV], 7 - seg)` | **`flag_test`** — проверка конкретного бита (M2-T2) |
| `digitalWrite(pin, bitValue ? HIGH : LOW)` | применение маски к «регистру» |

Так что M2-T2 будет не абстракцией, а формализацией того, что ты уже умеешь руками.

### Замечания

**1. Затенение переменной (shadowing) — самое важное:**

```cpp
for (int i = 0; i < aDigs; i++) {          // внешний i
    int digInd = 3 - i;
    for (int i = 0; i < 4; i++) { ... }    // ← ВНУТРЕННИЙ i перекрывает внешний
```

Работает, но `-Wshadow` ругается не зря: при любой правке легко взять не тот `i`.
Переименуй внутренний в `k`.

**2. Нет проверки выхода за границы:**

```cpp
int curDigV = digits[digInd];
... bitRead(digs[curDigV], 7 - seg) ...
```

Если в `displayNum` передать значение больше 9 (или отрицательное), `digs[curDigV]` —
чтение за пределами массива. В твоём коде `loop()` передаёт только `% 10`, так что
сейчас безопасно, но функция небезопасна сама по себе. Добавь `curDigV %= 10;` или
assert. На микроконтроллере такое падение выглядит как загадочный глюк.

**3. Типы:** `millis()` возвращает `unsigned long`, а `secs` у тебя `long`. Практически
безвредно (`secs %= 10000` держит значение маленьким), но согласование типов — полезная
привычка; `-Wsign-conversion` ловит такие места автоматически.

**4. Четыре параметра вместо значения.** `displayNum(int dig1, int dig2, int dig3, int dig4)`
вынуждает вызывать его с уже разобранным числом, а разбор делается в `loop()` вручную.
Лучше:

```cpp
void displayNum(long value);   // внутри — разбор на цифры циклом
```

Это ровно переход к модулю 3 (массивы вместо списка однотипных параметров).

**5. Стиль:** отступы плавают (2 пробела и 1 вперемешку), `i++` / `++i` непоследовательно.
`clang-format` + `-Wshadow` закроют оба пункта.

**6. Идея на будущее:** этот проект — отличный кандидат на финальный проект модуля 10,
но в более системном виде: симулятор таймера/регистра на чистом C с побитовыми масками
и дампом состояния, который потом один в один переносится на железо. То есть сначала
модель на ПК с автотестами, затем прошивка. Так работают в настоящем embedded.

```bash
EOF

```

После этого `git status` перестанет показывать бинарники, а история не будет ими раздуваться.
