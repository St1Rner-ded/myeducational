## M2-T1 · `count_ones_v1` — потеря старшего бита

```cpp
for (int i = 0; i < 31; i++) {
    if (n == 0) break;
    if (n % 2 == 1) c++;
    n = n >> 1;
}
```

Три падения:

| вход | твой ответ | верный |
|---|---|---|
| `0x80000000` | 0 | 1 |
| `0xFFFFFFFF` | 31 | 32 |
| `0xDEADBEEF` | 23 | 24 |

Все три — числа **с установленным старшим (32-м) битом**. Диагноз ставится по самим
тестам, даже не глядя в код: «не дохожу до последнего бита». `i < 31` проверяет биты
0…30, то есть 31 бит из 32.

Это умение стоит прокачивать отдельно: **читать падения тестов как диагностическую
информацию**, а не как «ну не работает». Закономерность в упавших входах почти всегда
указывает на причину.

### Претензия не к числу 31, а к тому, что условий остановки два

```cpp
for (int i = 0; i < 31; i++) {
    if (n == 0) break;      // ← этого уже достаточно!
```

`if (n == 0) break;` останавливает цикл, когда биты кончились. Значит счётчик `i`
не нужен вовсе:

```cpp
int c = 0;
while (n != 0) {
    if (n & 1u) ++c;
    n >>= 1;
}
```

И ошибка стала бы **невозможной**: нет счётчика — нечему ошибиться на единицу.

> **Правило:** если у цикла два независимых условия остановки — одно из них лишнее,
> и именно в нём живёт баг.

### Как узнавать ширину типа, а не писать 31 руками

В задаче было «ровно 32 итерации (или 64 — подумай, от чего зависит)». Зависит от:

```c
#include <limits.h>
8 * sizeof n            /* 32 для unsigned на x86-64 */
CHAR_BIT * sizeof n     /* то же, но переносимо: CHAR_BIT = 8 */
```

Если нужен именно фиксированный проход по всем битам (без раннего выхода):

```c
for (unsigned i = 0; i < CHAR_BIT * sizeof n; ++i)
    c += (int)((n >> i) & 1u);
```

### Мелочи оформления

- `n % 2 == 1` → `n & 1u`. Для `unsigned` оба дают 0/1, но побитовая запись
  идиоматичнее и не зависит от знаковости типа (для `int` `% 2` бывает `−1`!).
- `n = n >> 1` → `n >>= 1`
- пробелы: `int c=0` → `int c = 0`, `i<31` → `i < 31`
- `i++` в C++ → `++i` (для встроенных типов разницы нет, но привычка пригодится
  на итераторах)

В репо сейчас лежат три скомпилированных бинарника:

```

```


Три проблемы:

1. **Не покрывает** `a.out` и `solutions/M2/t`.
2. **`.gitignore` не действует на уже отслеживаемые файлы.** Их нужно сначала вынуть
   из индекса командой `git rm --cached`.
3. Игнорировать `test.cpp` рискованно: напишешь там настоящий тест — и он молча
   не закоммитится. Для черновиков заведи папку `scratch/` и игнорируй её целиком.

Как починить:

```bash
cd myeducational
git rm --cached solutions/L0/t solutions/L0/a.out solutions/M2/t
# заменить .gitignore на готовый (лежит в архиве update-2026-09-14.zip)
git add .gitignore
git commit -m "убрать артефакты сборки из репо"
git push
```

История коммитов (`ADDD`, `UPDATE`, `check solutions`, два merge-коммита) — тоже
повод навести порядок. Сообщение коммита должно отвечать на вопрос «что изменилось?»:
«решена M2-T1 v2», а не «ADDD». Merge-коммиты появились потому, что ты коммитил с
сайта и локально без `git pull` перед этим; лечится привычкой `git pull` → правки →
`git add` → `git commit` → `git push`.
