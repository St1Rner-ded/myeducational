# Простые числа: как определяется простота алгоритмически

Разбор твоего `L0-T2` и заодно — ответ на вопрос «что-то хромает понимание».
Хромает оно не у тебя одного: это первая задача, где наглядно видно разницу
между **«подобрал под тесты»** и **«построил алгоритм»**.

---

## 0. Что у тебя написано сейчас

> **Алгоритм** — правило, работающее для любого входа из области определения.
> **Перечисление случаев** — это не алгоритм, оно ломается на первом же непредсказанном входе.

## 1. Определение → наивный алгоритм

Число `n` **простое**, если `n > 1` и у него ровно два натуральных делителя: `1` и `n`.
Единица — **не простое** (и не составное): иначе разложение на простые множители
перестало бы быть единственным.

Наивная реализация определения в лоб:

```
если n < 2 → не простое
для d от 2 до n-1:
    если n делится на d → не простое
простое
```

Сложность **O(n)**. Для `n = 1 000 000 007` это миллиард итераций — секунды работы.
Неприемлемо, тем более что ответ находится намного раньше.

---

## 2. Ключевая идея: делители ходят парами

Если `d` делит `n`, то `n / d` **тоже** делит `n`. Делители всегда приходят парами:

**n = 36** (√36 = 6)

| пара | произведение |
|---|---|
| 1 × 36 | 36 |
| 2 × 18 | 36 |
| 3 × 12 | 36 |
| 4 × 9 | 36 |
| **6 × 6** | 36 ← пары «схлопываются» ровно на √n |

```
делители:  1   2   3   4   6   9   12   18   36
                       ↑
                      √36
           |←— тут искать —→|←— тут уже всё зеркально —→|
```

**n = 97** (√97 ≈ 9.85) — простое: единственная пара `1 × 97`.
Достаточно проверить `d = 2…9`: ни одно не делит → простое.

### Почему этого достаточно (доказательство в две строки)

Пусть `n = a · b`. Предположим, **оба** множителя больше `√n`:

```
a > √n  и  b > √n   ⇒   a · b > √n · √n = n
```

Но `a · b = n`. Противоречие. Значит, хотя бы один множитель **≤ √n**.

> **Следствие:** если у `n` есть нетривиальный делитель, то обязательно найдётся
> делитель, не превосходящий `√n`. Поэтому перебирать дальше `√n` бессмысленно —
> любой «дальний» делитель уже был бы найден как пара к «ближнему».

Сложность падает с **O(n)** до **O(√n)**.

---

## 3. Сколько это в реальных числах

| n | √n | итераций (нечётные, шаг 2) |
|---|---|---|
| 1 000 | 31 | ~15 |
| 1 000 000 | 1 000 | 500 |
| 1 000 000 007 | 31 623 | 15 811 |
| 2 147 483 647 (`INT_MAX`, простое) | 46 341 | 23 170 |

Вот почему `1000000007` проверяется **мгновенно**: 15 тысяч итераций — это
микросекунды. А наивный перебор до `n-1` — миллиард итераций, секунды.

## 4. Как писать условие цикла — тут зарыта мина

Есть три варианта, и два из них плохие.

| Вариант | Вердикт | Почему |
|---|---|---|
| `d <= sqrt(n)` | ❌ | `sqrt` работает с `double`: потеря точности на больших `n`, медленнее, нужен `<cmath>` |
| `d * d <= n` | ⚠️ опасно | **`d*d` может переполниться** — и это UB |
| `d <= n / d` | ✅ | деление не переполняется никогда, целочисленно, быстро |

### Реальная катастрофа на ровном месте (проверено, gcc 12 + UBSan)

```c
int n = INT_MAX;                     /* 2147483647 — ПРОСТОЕ число */
for (int d = 3; d * d <= n; d += 2)
    if (n % d == 0) return false;
```

Что происходит:

```
ovf2.c:6:23: runtime error: signed integer overflow:
             46341 * 46341 cannot be represented in type 'int'
```

`√2147483647 ≈ 46340.95`, поэтому на `d = 46341` произведение `d*d = 2147488281`
не влезает в `int` (максимум 2147483647) и **уходит в отрицательные числа**.
Условие `отрицательное <= n` остаётся истинным, цикл не останавливается там, где должен,
и в итоге:

- работает **15 секунд** вместо микросекунд,
- выдаёт **неверный ответ**: «делитель 2147483647» → число объявлено составным,
  хотя `INT_MAX` простое.

Тот же цикл с `d <= n / d` — мгновенно, корректно, без UB.

Это лучший пример того, почему в нашем курсе везде `-fsanitize=undefined`:
**одна запись условия дала и UB, и неверный ответ, и тормоза в тысячу раз.**

## 5. Дальнейшие ускорения

**1. Вынести двойку, идти шагом 2.** Половина чисел отсеивается сразу:

```
если n делится на 2 → ответ «n == 2»
дальше d = 3, 5, 7, 9, ... (d += 2)
```
Ещё вдвое быстрее. Это обязательный минимум.

**2. `6k ± 1`.** Все простые больше 3 имеют вид `6k±1` (остаток 0, 2, 3, 4 от деления
на 6 делится на 2 или 3). Проверяем только их — ещё в 1.5 раза быстрее. Красиво, но
не обязательно на этом этапе.

**3. Решето Эратосфена.** Если нужно найти **все** простые до N или проверять много
чисел подряд — перебор делителей каждый раз расточителен. Решето строит таблицу
разом за `O(N log log N)`: вычёркиваем кратные 2, затем 4, затем кратные 3, 5, …
Память `O(N)`. Отдельная задача на модуль 3 (массивы) — она того стоит.

**4. Миллер–Рабин.** Вероятностный тест, `O(k · log³n)`. Именно им я проверял числа,
когда готовил для тебя тесты. Для учебных задач не нужен, но знать о его существовании
полезно: перебор делителей неприменим к 200-значным числам, а в криптографии работают
именно с такими.

## 7. Чек-лист частых багов (твой случай помечен)

| Баг | Симптом |
|---|---|
| забыть `n < 2` | `is_prime(1)` и `is_prime(0)` → true |
| забыть отрицательные | ⚠️ **твой**: `is_prime(-11)` → true |
| «чётное ⇒ составное» без исключения | `is_prime(2)` → false |
| перебор вместо `√n` (до `n/2` или `n-1`) | работает, но медленно; на больших `n` — таймаут |
| `d * d <= n` | UB + неверный ответ на больших `n` (раздел 4) |
| `int d` при `long long n` | то же переполнение, только незаметнее |
| фильтр по мелким делителям | ⚠️ **твой**: 121 → true |
| `return true` внутри цикла | первое же непроверенное число объявляется простым |
| `d <= sqrt(n)` | теряется точность на больших `n` |

## 8. Мета-урок: «тесты прошли» ≠ «работает»

Твоё решение прошло **все 10 моих исходных тестов**. Это главный урок задачи, и он
важнее самих простых чисел:

> **Тесты не доказывают корректность. Тесты доказывают некорректность.**
> Пройденные тесты означают лишь «на этих входах совпало».

Как с этим жить — перед сдачей любой задачи задай себе три вопроса:

1. **Какой вход сломает моё решение?** Для фильтра по делителям 2,3,5,7 ответ находится
   за секунду размышления: `11 × 11 = 121`.
2. **Что мой код делает на границах?** 0, 1, 2, отрицательные, `INT_MAX`, `LLONG_MIN`,
   пустой массив, максимальный размер.
3. **Моё решение — это правило или перечень?** Если в коде перечислены конкретные
   числа-исключения (`n==2 || n==3 || n==5 || n==7`) — почти наверняка это заплатка,
   а не алгоритм. Исключения допустимы, когда они *выводятся* из математики
   (2 — единственное чётное простое), а не *подбираются* под тесты.

Я на своей стороне сделал то же самое: понял, что мои тесты не ловят такую заплатку,
и добавил 10201, 10403, 3215031751 и другие. Ошиблись оба — разница в том, что
тесты усиливаются один раз, а привычка «придумай злой вход» работает всегда.
